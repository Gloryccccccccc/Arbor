# 05 执行 Harness 与验证沙箱

Harness 在这里指控制 Agent 执行的运行框架与约束。Pi 提供基础循环和会话，SDKMorph 增加升级任务契约、受控工具、预算、持久化与完成门槛；它不等于整个产品架构。

## 执行与权限边界

- 任务输入固定为项目快照、源与目标版本、允许修改范围和验证策略。独立工作区用于保护用户原项目；Git worktree 本身不提供安全隔离。
- 仓库代码、安装脚本和测试在任务容器中运行；扫描模式可以不要求 Docker，缺少容器环境时阻止自动执行，不静默降级为宿主任意 shell。
- 容器不挂载宿主 Docker socket、模型密钥目录或 SSH 凭据；Docker 调度由外层受控 launcher 承担。
- Pi 工具替换为受控实现：读写限制在任务工作区，检查真实路径、符号链接与越界访问；命令执行转交 runner。
- 设置总时限、调用次数、修复轮次和输出大小限制。取消同时处理模型请求、工具子进程与容器，保留已完成证据。
- 模型凭据由 VS Code SecretStorage 管理，日志进行脱敏；文档和仓库内容仅作为任务数据，不可修改权限与验收规则。

## 验收设计

先在原版本与冻结代码上建立基线，再对候选补丁运行目标环境验证。独立验证在干净环境重新应用候选补丁，使用保护的测试与固定配置。若补丁更改测试，需要单独审阅，不能用删除断言或跳过测试获得成功结论。

- 区分依赖安装、导入、类型或静态检查、原项目测试、迁移合同测试和补充行为检查的结果。
- 基线已失败的用例单独报告；不把失败数量相同当成行为未变。
- 每次修改补丁后，旧验收结论失效。报告关联代码、锁文件、镜像、知识包与验证规则的哈希。
- 测试通过只说明已执行检查通过，不证明所有业务行为等价；业务语义变化需要明确的验收标准。

## 恢复与适用范围

会话恢复不代表副作用恢复。重启后先核对补丁、容器、环境和产物，再从有效检查点继续。第一版只承诺在受支持环境中处理可信或受控案例；容器是隔离的一部分，不宣称具备抵御任意恶意仓库的完整多租户安全能力。
