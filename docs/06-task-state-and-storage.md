# 06 任务状态与数据存储

本地插件的任务记录采用 SQLite 与任务产物目录作为首选方案；驱动选择须考虑最低 Node 版本和跨平台打包。领域接口保持可替换，先解决单用户持久化，不把多实例并发能力作为既成事实。

数据库是必需的持久化能力。SQLite 需要实施事务、表结构迁移、索引、修订与恢复设计；选择本地数据库是为了让插件用户无需部署数据库服务。

## 数据对象

| 对象 | 保存内容 |
| --- | --- |
| ProjectSnapshot | 工作区标识、代码快照、未提交改动、依赖声明与锁文件哈希 |
| UpgradeTask | SDK 源与目标版本、阶段、预算、取消状态、失败原因、检查点 |
| TaskEvent | taskId、单调序号、时间、事件类型、脱敏摘要 |
| Evidence / Artifact | 文档证据、补丁、环境清单、测试结果与产物哈希 |
| VerifiedExperience | 人工确认或独立验证后的迁移经验、适用范围、来源与失效条件 |

## 任务状态

计划阶段状态：created → analyzing → awaiting_start → preparing → baseline → migrating → verifying → review_required → applied。blocked、failed、cancelled 为明确分支；只有补丁已通过指定验证才进入可审阅成功结果。review_required 不等于已应用，applied 不等于已合并或发布。

事件用于展示与审计，持久化任务状态用于恢复。写入检查点时保存对应产物；恢复前核对哈希。依赖安装、补丁应用等有副作用步骤使用操作 ID 和现场检查，不能靠重放所有事件实现重试。

## 任务记忆、Trace 与检查点

| 对象 | 回答的问题 | 使用方式 |
| --- | --- | --- |
| Trace / TaskEvent | 发生过什么工具调用，输入输出、耗时和结果如何 | 展示执行过程，定位问题和追溯证据 |
| 任务记忆 | 当前目标与约束是什么，已确认什么，哪些尝试失败，还剩什么问题 | 构建下一轮上下文，帮助持续执行 |
| 任务状态与检查点 | 处于哪个阶段，当前产物是什么，是否满足继续执行条件 | 由状态机与工具维护，恢复前核对现场 |

任务记忆不是完整 Trace 的副本。恢复时先读取状态快照和结构化工作笔记，再按引用查询相关 Trace；不要求模型重新阅读所有执行流水。最终阶段、文件哈希和验证状态由程序维护，模型生成的笔记不得修改这些权威字段。

## Memory 与缓存

- 任务记忆：已确认事实、约束、证据、失败尝试和待解决问题；与原始会话分开保存。
- 跨任务经验：仅保存已验证内容，附 SDK/版本/环境条件；不把模型自报成功自动写成长期经验。首版可先人工审核。
- 缓存：文档按内容哈希与检索模型版本，代码分析按快照与分析器版本。语义相似不代表补丁可以直接复用。

记忆按工作、任务、项目、迁移经验四种用途组织，共用 SQLite 与文件存储。工作记忆是本轮送入模型的信息；项目记忆是按仓库隔离的长期记忆；迁移经验是有适用条件的历史案例。详细生命周期、检索与上下文压缩设计见[《09 分层记忆与上下文压缩》](09-memory-and-compaction.md)。

建议持久化 TaskCheckpoint、MemoryRecord 和 CompactionRecord：分别记录任务修订与产物指纹，记忆作用域、来源与失效状态，以及摘要覆盖的事件范围、任务修订和原文引用。表名与驱动将在实现阶段确定。

## 数据与文件边界

- SQLite 保存任务、知识元数据、记忆、产物索引和结构化执行结果；大日志、代码快照与补丁存入任务产物目录，数据库保存引用和哈希。
- 模型凭据保存在 SecretStorage，不写入会话摘要或经验记录；原始会话和日志按脱敏与保留策略管理。
- 本机开发数据、会话和临时文件配置到 E:\项目\SDKMorph\.work；插件分发后使用独立、可配置的数据目录，生成文件不进入受迁移项目的 Git 提交。
- 更新任务状态与检查点时用事务和修订检查；重启后核对代码、环境、容器与产物，防止拿旧记忆继续操作新状态。

## MySQL、Redis 与 Milvus 的位置

这些组件从本地首版移到服务端扩展候选：MySQL 承担团队和任务事实，Milvus 承担有实测需求的共享向量索引，Redis 在出现真实队列或分布式限流需求时再加入。Memory 是数据与生命周期设计，不等同于 Redis，也不必须使用向量库。
