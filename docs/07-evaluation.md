# 07 评估方案与案例集

评估的目标是确认版本知识、领域工具和独立验收是否带来实际收益，并暴露失败边界。本文是实验计划，没有已完成的评测结果。

## 案例准入

- 明确 SDK 源与目标版本，固定项目代码、Python 环境与依赖解析结果。
- 优先选择存在官方迁移说明、可离线模拟外部服务、具有可执行测试的案例。首个 SDK 与版本对尚待盘点后确定。
- 覆盖接口改名、参数或返回结构变化、同步异步变化、异常处理变化、项目封装与依赖冲突。
- 每个案例保存原版本可运行基线、升级触发的问题和预先制定的验收条件；验证测试与 Agent 可修改目录分离。
- 训练或调试案例与保留评估案例分开，公开来源注明许可，合成项目明确标为合成案例。

## 对照组

| 组别 | 用途 |
| --- | --- |
| 仅升级依赖 | 判断案例是否确实需要调用代码迁移 |
| 可用的确定性迁移工具 | 判断规则本身可以解决多少问题 |
| 同一 Pi 基础执行器 + 通用任务说明 | 控制模型与工具执行器后，评估领域方案的增量价值 |
| SDKMorph 完整流程 | 版本检索、领域工具、状态管理与独立验收 |
| 消融组 | 分别移除版本过滤、技能或经验，检验新增组件是否值得保留 |

比较时固定任务输入、可访问资料与工具、模型版本、时间及调用预算、验收规则。预算和实际消耗分别记录；不拿高预算方案与低预算基线直接比较成功率。每组重复运行，保留失败与波动，不只展示最佳一次。

## 指标与失败归因

- 独立验证通过率、错误宣告成功率、人工修改量、耗时与模型调用成本。
- 版本证据命中率、版本误匹配率、无依据修改与超范围修改。
- 任务取消是否终止执行、重启恢复成功率、事件与产物是否一致。
- 区分环境失败、知识缺失、定位失败、补丁错误、测试覆盖不足和预算耗尽。

## 面试展示材料

准备一个成功升级、一个需要人工决策、一个明确阻塞的完整案例。说明选择、证据、执行与限制。简历只填写真实实施与实测结果，不把设计目标写成已有收益。
