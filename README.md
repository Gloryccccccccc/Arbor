# SDKMorph

面向 Python 项目的 SDK 版本管理与自动升级插件。

SDKMorph 计划通过版本变更知识、代码影响分析和执行反馈，完成 SDK 升级中的调用代码迁移，并为开发者提供补丁、迁移依据和验证结果。

**当前处于设计阶段。仓库先维护方案与验收标准，尚未提供可安装插件或已实现的升级能力。**

## 使用流程

1. 扫描项目依赖，识别声明约束、锁定版本和目标版本。
2. 检索适用的迁移文档，定位受影响的调用代码。
3. 在独立工作区建立原版本基线，执行升级和有限次数的反馈修复。
4. 独立验证候选补丁，展示通过、失败与未验证项。
5. 用户审阅 Diff 并主动接受补丁。

首版限定为桌面 VS Code、单个 Python 仓库、单个 SDK 的明确版本升级。首个 SDK 和版本对将在案例盘点后确定。

## 技术方案

| 部分 | 计划技术与职责 |
| --- | --- |
| 插件入口 | TypeScript + VS Code API，提供命令、依赖视图、进度和 Diff |
| 领域核心 | TypeScript，负责版本快照、任务状态、预算、恢复和验收策略 |
| 编码执行器 | 独立 Node Worker 托管 Pi TypeScript SDK，接入受控工具 |
| 执行与验证 | Docker 隔离仓库代码和测试执行，独立验证候选补丁 |
| 本地状态 | SQLite 与任务产物目录；驱动和运行时兼容性待验证 |
| 版本知识 / RAG | 带来源、版本范围和内容哈希的知识包；关键词与符号检索为基线，评估语义召回的增量收益 |
| 记忆与上下文 | 工作、任务、项目与迁移经验分层；任务/项目记忆、检查点和受控压缩优先实现 |
| 工具接入 | Pi 直接注册领域工具；MCP 作为复用核心服务的后续接入方式 |

Python 是被迁移项目的目标语言与执行环境，主体不额外引入 Python 后端。用户无需部署 MySQL、Redis 或 Milvus；服务端协作属于后续扩展。

## 实施路线

- M0：确定一个 SDK 版本对，验证 Pi 集成、运行时、打包与容器工具的可行性。
- M1：完成插件入口、任务事件与取消，生成可安装的 VSIX。
- M2：完成版本感知 RAG、影响分析、迁移与独立验收闭环，接入任务/项目记忆和受控压缩。
- M3：验证失败恢复、预算边界、压缩与过期记忆处理，完成对照评估。
- M4：小范围试用后，发布到 VS Code Marketplace。

评估将记录独立验证通过率、错误宣告成功率、人工修改量、耗时与调用成本。尚无实测结果，不承诺任意 SDK 升级成功或完整行为等价。
